# Jev 类目辅助判断接入评估

2026-09-21。参考任务：`01a0c381-af88-7b80-9818-7f653491c08f`（排查款号类目映射错误 (2)）。本次读取任务及原始请求/响应、复核两轮统计，并阅读 TypeSafe skill 和实时 API/置信度文档。未修改生产配置、业务代码或已提交的官方优先修复；未重复发起模型请求。

## 结论

有接入价值。推荐先增加**官方类目的语义映射建议与影子评估**，用于现有规则找不到等义类目、多个候选难以区分的情况。已明确的官方映射仍走确定性规则；模型不能推翻官方来源优先、资格限制或人工选择。

当前皮靴→靴子已由本地 commit `5c9e8af` 修复，无须再依赖远程模型解决这个已确定的问题。

## 独立复核的证据

全品类实验使用 `jev-1.13.0`，官方发布类目为唯一商品语义输入；候选取线上电商巴拉巴拉、商家 1162 的深绘缓存，并根据官方路径先做大类路由。

统计限制：

- 79 种原始输入，按实验的 `normalizedOfficial` 归一后只有 **53 种**；空白、分隔符的不同写法也形成了实验样本。
- 79 种中仅 42 种有唯一预期 ID，其余采用多候选可接受集合；全部预期由助手在调用前定义，尚未独立业务验收。
- 78/79 中未命中的包类样本实际返回 `NEEDS_REVIEW`，属于弃判，不是选中了错误类目；不能混用语义命中率、自动推荐覆盖率和错误应用率。
- 37 次请求包含批量与两阶段调用，45.32 秒不是单款延迟，也不是 P95；74/74 只代表本次运行，没有证明长期可用性。
- 缓存含 1,888 个节点，评测政策范围选出 336 个节点，再按服装、鞋、配饰等路由。范围内结果两轮都没有选到缓存中的父节点，但接口候选确实包含父节点，生产仍须校验可选性。
- 鞋类两轮均符合事前预期，包括皮靴和凉拖鞋。但之前仅官方字段、58 个鞋类候选的小样本曾出现皮靴弃判和凉拖鞋选凉鞋，说明候选构造与提示会影响结果。

## 需要代码兜住的边界

1. **年龄/性别不能靠模型补造。** 官方帽子未写年龄，模型仍选“婴童配件 / 帽子”，置信度可达 0.98；背心会在“中大童 / 背心/吊带”和“吊带”之间变化。高置信度不是业务资格证明。对无年龄的官方输入，先优先保留等义且不限定年龄的候选；如果深绘只有年龄分支而业务未明确其适用口径，应待确认，不宣称来源已提供年龄。
2. **模糊复合类目会变动。** 背心吊带、连身衣、包类是本次 ID 变化集中位置。多个合理候选时应展示建议，不自动覆盖已有结果。
3. **缺官方就没有模型判断依据。** 在仅官方输入的既定口径下，之前 30 款缺官方证据问题不会被 Jev 自动解决。保持现有回退逻辑或提示补来源，不能偷偷改传唯品/抖音。
4. **官方本身多值不能用模型投票。** `204326146011`、`204326146110` 仍由规则判定为需确认。
5. **不适用范围在代码拦截。** 实验发现部分婴童用品等边界会被强选成宽泛服饰类别；不要依赖模型自行拒绝。
6. **置信度是候选分布的集中程度。** 不是整体正确率，也不是应用权限。不能先拍一个 0.8 或 0.9 就启用自动修改；NEEDS_REVIEW 的高置信度尤其不能解释为分类成功。

## 在 Listingify 中如何放置

流程：官方来源读取 → 确定性规则 → 必要时生成 Jev 建议 → 代码验证候选/来源版本/资格 → 展示建议或待确认。

- 现有规则唯一命中：直接使用规则；上线初期可以抽样在后台比较 Jev，不增加用户等待。
- 官方非空但缺少名称映射、或规则同分：在对应大类候选内调用 Jev `Choice`，允许 `NEEDS_REVIEW`。
- 模型与规则不同：只记录差异，供开发/业务检查。尤其已修复的官方皮靴→靴子，不让模型弃判反过来破坏规则结果。
- 人工已选、已提交、已发布：模型只能提出建议，不能覆盖。
- 模型不可用、超时或返回不合法：原规则和草稿状态保持原样，建议标为不可用。

### 候选构造

候选从正确租户/商家的 `deepdraw_trade_cache` 动态生成，沿用当前允许的根和分支。先根据官方完整路径区分鞋、服装、配饰，不把整棵树交给模型。

保留等义名称映射及完整路径；排除不可提交父节点、停用/待删节点。平台、尺码和年龄/性别资格由代码负责。候选缺资格时应记录“语义匹配但不可用”，不能让模型为满足资格改选另一鞋型。

单个 Choice 最多 255 选项。超限时按真实树分层或稳定的语义子树划分，再决选；不要任意截前 255 个。不同候选组的概率不能直接横向比较。记录每阶段候选与结果，验证正确答案是否在第一阶段被遗漏。候选顺序固定有助复现，但不能用固定顺序掩盖本次发现的敏感性。

### 接口与服务边界

TypeSafe 使用 `POST /v1/systemone`，输入 `model/state/questions`，返回类型化 choice、probabilities、confidence；不是文本解释模型。

Listingify 的 `ai_scenario_router.mjs` 当前主要对接 OpenAI `/chat/completions` 和 Anthropic `/v1/messages`，不能把 TypeSafe base URL 与模型名直接塞入现有协议。建议新增小型服务端 `typesafe_client.mjs` 适配器，复用现有哈希/日志/用量审计设施，避免修改无关模型路由。

保持 `evaluateDeepdrawTradeSelectionFromLaunchPlanRows` 的同步纯规则入口。在异步服务或后台任务中执行建议请求，再持久化建议结果；不要在每次列表/详情读取时同步访问远程模型，也不要在数据库事务中等待网络。

配置可采用 `AI_SCENARIO_DEEPDRAW_CATEGORY_ADVICE_MODE=off|shadow|suggest`：第一期默认 off，随后按租户开启 shadow，最后开放人工可见 suggest。API key 只放服务端环境或现有密钥存储，不复制实验项目的 `.env`，不落入前端或请求日志。

### 数据、缓存与展示

建议单独记录 `modelVersion/questionVersion/policyVersion/inputHash/candidateHash/officialSourceBatchId/rawChoice/probabilities/confidence/status/createdAt`。已有 `withAiRoutingHashes` / `hashAiRoutingValue` 可复用。

相同“官方规范化类目 + 候选快照 + 政策 + 模型/问题版本”可共享语义结果；商品最终资格必须逐款重新检查。若候选已按 SKU/平台筛选，其结果集必须进入 candidateHash。规范化保留原始文本和变化记录，不删除影响含义的叶子、复合词或年龄限定。

UI 显示“官方类目”“规则推荐”“AI 建议”“可应用/不可应用原因”；解释由代码根据证据和资格生成，不能把不存在的自然语言推理冒充 Jev 原始输出。应用时再次核对来源版本、候选及人工锁定，防止旧结果覆盖新状态。

## 最小落地阶段

1. 固化当前官方优先规则及真实回归集。
2. 加专用客户端、输出结构校验、超时/有限重试、脱敏审计和缓存；候选需包含 NEEDS_REVIEW。
3. 后台影子运行，只记录模型与规则差异，不改推荐或草稿；按规范化类目计数，另附款号覆盖。
4. 对有增量价值的样本建立独立业务标签与留出集，测自动建议覆盖、错误建议、弃判、顺序稳定、分支合法性、平台/尺码可用性及端到端延迟。
5. 达标后仅开放“AI 建议＋人工采用”；是否自动应用另行确定，不能从小样本语义预期命中推导上线许可。

验收重点是：相比当前官方优先规则，Jev 实际解决了多少原本无法判断的输入，是否引入额外错误或等待。对已经确定的 433 款官方鞋类结果重复调用模型，不是主要收益来源。
