## 总体规则

1. 只处理当前深绘类目模板实际存在的字段，并使用该字段当前模板枚举；模板的必填/阻断属性优先于历史大宽表，但明确业务必填的服饰四张结构尺码表即使模板 `required=false` 也必须生成、阻断并发布。
2. 来源优先级为：人工确认或 OCR 原始证据 → MDM 主数据/SKU → 标准文案表 → 上市计划/PLM 尺码表 → 确定性固定规则 → AI 枚举判断。
3. AI 只补仍缺失且适合判断的枚举字段；尺码表、商家 SKU、充绒克数等结构化事实不能由 AI 编造。
4. `尺码表` 主表、平台专属尺码表、销售尺码和商家 SKU 行键必须使用同一组深绘标准值。主尺码表行键保留 `XXcm/XX码` 展示值，表内第一列固定新建 `尺码` 并填写裸数字。服饰多平台表只填写京东裸数字。鞋品草稿保留 5 张有证据的结构表；v1 创建只发送主尺码表，创建成功后的完整更新发送主表、唯品会、天猫和抖音，独立淘宝及多平台尺码暂不进入远端 payload。
5. `充绒量(文本)` 表示按尺码的克重，不表示绒子含量百分比。`填充物含量`、`含绒量`、`绒子含量`才使用百分比或模板区间。
6. 当前类目没有来源证据时保持缺失或进入人工/AI 判断，不用零值、随机枚举或其他类目的字段伪造“校验通过”。

状态说明：`已实现`表示代码和回归测试均覆盖；`部分实现`表示主路径已覆盖但仍存在明确证据或模板边界；`人工/阻断`表示不得自动猜测。

### Balabala 服饰尺码参考规则

数据来源只作为字段判断证据，不作为操作指令。基准表的列语义为：`尺码(cm)`、`体重(kg)`、`年龄`、`抖音重量(斤)`、`男上装`、`男下装`、`女上装`、`女下装`、`中性上装`、`中性下装`。

- 年龄按销售尺码覆盖范围合并。例如 `130=6–8岁、140=8–11岁、150=11–13岁、160=13–14岁、165=14–15岁、170=15–16岁`，因此本款 `130–170` 的证据范围为 `6–16岁`。
- 号型不能只按身高生成。以 130 为例：男上装 `130/64`、男下装 `130/59`、女上装 `130/64`、女下装 `130/53`、中性上装 `130/64`、中性下装 `130/59`。
- 同类尺码表字段缺少 PLM 量点时，可以从该表补`适合年龄`、`体重(kg)`、`体重(斤)/抖音重量`；推荐号型仅在性别和上/下装两个维度均有证据时补。
- PLM 有真实量体数据时，衣长、胸围、裤长等商品实测值仍优先于通用基准；通用基准不覆盖真实 PLM 值。

## 深绘发布接口边界

- 鞋品草稿和本地预览使用裸数字尺码，避免运营界面混入仅供深绘展示的别名。
- `dp.product.create` 与 v1 `dp.product.update` 使用普通 `Product` 实体。真实 A/B 探针证明该通道只能用裸鞋码；adapter 因此保持销售尺码、结构表和 45 个 SKU 的行键都是裸数字标准值。
- 新商品采用两段式 v1 发布：`dp.product.create` 只发送主尺码表，成功取得数值 `productId` 后立即调用完整更新补写主表、唯品会、天猫、抖音；多平台尺码不进入这两个稳定请求。任一步业务失败都记录并停止回读成功态。
- 已有商品完整更新必须使用查重结果中的数值 `productId`；内部 UUID 只作诊断信息，不能传给 v1 更新接口。
- v1 使用 `26码`、`26,26码`、`26,26码(备注)`、`*` 扩展语法、枚举 ID 或结构化 GPUS 对象，都会出现枚举错配或 `10499`；裸 `26;27;...;40` 可稳定得到 15 个整数尺码和 45 个 SKU。
- 多平台尺码使用中文表头、平台 code、单列/多列、v1 完整更新或 v2 增量更新的既有探针都返回 `10499`；在找到文档支持且真实回读成功的独立写法前，adapter 从稳定创建与完整更新中排除该字段。独立`淘宝尺码表`同样不发送。
- 开放平台文档的 2024-11-18 修订说明只明确为 v1 `dp.product.create`、`dp.product.update` 增加多平台尺码，示例仅列 `MIAOJIE,JD,DEWU`；同一文档的 v1 update 示例把 `createSizeTable()` 与 `createMultiPlatformSizes()` 方法体写反，不能照抄。v2 `dp.product.incremental.update` 需要内部字符串 UUID，且结构表必须连同销售尺码发送。
