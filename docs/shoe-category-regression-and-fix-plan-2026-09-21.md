### 67 个待确认的原因

- 官方户外鞋与唯品具体分类不一致：17 款。
- 学步与步前阶段不一致：2 款。
- 只有泛化休闲鞋证据，不能唯一确认板鞋：27 款。
- 官方皮靴与唯品款式棉拖不一致：1 款。
- 雪地靴与其他平台具体分类不一致：2 款。
- 官方板鞋与其他平台学步鞋分类不一致：2 款。
- 官方皮靴与唯品学步鞋或皮鞋分类不一致：3 款。
- 凉拖鞋与袜子分类不一致：2 款。
- 步前鞋与袜鞋复合类目，需确认鞋袜语义：5 款。
- 同一官方类目字段存在多个值，保留来源冲突：2 款。
- 唯品复合类目不足以唯一确认板鞋：3 款。
- 皮鞋与抖音拖鞋分类不一致：1 款。

这些分类差异有的可能是平台分类口径不同、年龄阶段与鞋型交叉，而非源表填错。保守处理是暂停自动选择并呈现证据，不擅自修改官方或唯品数据。

典型例子：

- `204426141012`：官方儿童户外鞋；唯品儿童皮靴/棉靴；抖音靴子。现算法推荐户外鞋，不能只靠提高靴子权重决定最终类目。
- `208426146014`：官方皮靴、抖音靴子，唯品学步鞋。需确认靴型与学步阶段在深绘中的落点。
- `204426146128`：官方学步鞋，唯品与抖音步前鞋/袜鞋。学步、步前不能视为同义词。
- `208426172022`：鞋类路径包含步前鞋/袜鞋，唯品是婴儿袜子。需要业务区分有鞋底的袜鞋与普通袜子。
- `2084261412G7`：只有休闲鞋、时尚生活鞋，缺少发布类目；无法证明就是板鞋。

## 根因：四处规则需要一起修

1. **宽泛别名与跨字段重复加分。** `LAUNCH_PLAN_CATEGORY_MATCH_ALIASES` 把休闲鞋、时尚生活鞋分别扩展到板鞋/运动鞋；`bestDeepdrawTradeMatch` 对每个字段累加分数，还重复叠加上下文分。多个来自同一业务分类体系的宽泛字段可压过明确发布类目。
2. **词义不统一、泛化层级错误。** 官方皮靴没有归一到深绘靴子；`isGenericOfficialCategoryLeaf` 把学步鞋、靴子归为可被“更具体上下文”覆盖的泛类目，但这个上下文并未限制为原鞋型内部的细分，允许跳到板鞋。
3. **对整条路径做子串别名匹配、候选范围过宽。** `launchPlanCategorySearchValues` 可从抖音父路径“鞋靴箱包”命中通用别名“包”；第一优先级又包含童装根，因此鞋类能进入童装包包候选。
4. **冲突和资格条件不是硬约束。** `launchPlanCategorySourceConflict` 只检测同一字段多值，未覆盖跨平台语义差异；原状态机即使 `sourceConflict=true` 仍可能 `auto_applied`。`bestOfficialCategoryLeafTradeMatch` 在平台过滤前计算，之后可选中没有平台覆盖的官方叶子结果。

代码锚点：`web/server/services/product-archive-drafts.ts` 中的 `launchPlanCategorySearchValues`、`bestDeepdrawTradeMatch`、`isGenericOfficialCategoryLeaf`、`bestOfficialCategoryLeafTradeMatch`、`evaluateDeepdrawTradeSelectionFromLaunchPlanRows`。

## 为什么不能只删别名或删除品类字段

对真实 534 款做“仅在内存中删去品类/小类”的对照：84 款推荐改变，其中 59 款失去推荐；3 款从学步鞋变成童装包包（`204426146128`、`208426146222`、`204325144002`）；还使 5 款运动鞋变成板鞋。说明泛化字段有兜底价值，但不能允许其跨鞋型压过明确证据。

这 3 个包包结果是故障注入/消融实验，**不是这 3 款当前线上的推荐结果**；当前均是学步鞋。

另一个故障注入：保留真实 `204426141011` 雪地靴来源，只清空目标雪地靴的缓存平台信息，现算法仍返回 `auto_applied/high`，`coveredPlatforms=[]`。方案原型改为待确认。该实验说明潜在过滤旁路，不表示当前线上雪地靴缓存真的缺平台。

## 完整修法

### 1. 增加鞋类专用的证据解析层

新增独立纯函数模块，例如 `product-archive-shoe-trade-selection.ts`，由现推荐入口在确认是鞋品时调用；服装及其他品类保持现有行为。

每条证据保留 `sourceRowId/sourceBatchId/sourceType/field/rawValue/normalizedLeaf/family/specificity`。分离路径层级、复合叶子和业务字段，不改写原始 `row_json`。把“唯品已上市”、空值、`0`、`/` 等状态或占位符当作缺少类目，并展示提示。标识字段来自不同历史批次的回退，避免看似同一版本的证据其实来自不同时点。

正式规则用稳定语义/配置与实时元数据解析 ID，ID 是本次缓存快照，不假设跨商家、跨租户通用。无目标或多个等价候选时待确认，不选第一个结果。

### 3. 先硬过滤，再分层排序

选择顺序固定为：

1. 鞋品领域与鞋配件领域边界；排除童装包包等无关候选。
2. 租户允许的深绘分支及目标叶子；保留必要祖先用于优先级判断，父节点不能作为最终可提交类目。
3. 必需平台覆盖、真实 SKU 尺码覆盖；缺失元数据记为未知并待同步/待确认，不当作已通过。所有官方叶子兜底也必须经过相同过滤，禁止绕过。
4. 明确发布类目形成鞋类约束。具体类别优先；“运动鞋”等宽泛类别只允许在已声明兼容关系内细分，不能任意覆盖学步、步前、靴类。
5. 在同一兼容类别内用其他发布类目、唯品具体款式、计划小类排序。泛化品类仅兜底，不跨类累加；同义/相关证据按来源组去重，上下文加分只计算一次。
6. 同一类别下优先可用的直接童鞋叶子；仅在直接叶子确实不可用时，依据明确性别考虑合法男童/女童分支。不能因为另一个鞋型的直接叶子存在，就全局排除当前鞋型的性别分支。

不要只把“官方权重 400 改成 1000”：会继续掩盖跨平台冲突，也解决不了路径子串与资格旁路。

### 4. 冲突必须改变自动应用行为

返回结构增加或补足：`selectionPolicyVersion`、`evidence`、`conflicts`、`rejectedCandidates`、`eligibility`、`autoApplyAllowed`。明确区分“唯一类目”“来源冲突”“来源不足”“缺平台”“缺尺码元数据/覆盖”。

- 来源一致且唯一、资格齐全：可自动应用，理由展示真实命中字段与约束。
- 跨平台分类不一致、复合类目未消歧、仅宽泛证据：`manual_selection_required`；允许展示候选列表，但不写默认类目，不自动提交。
- 推荐与已应用不一致：保持已有 `appliedTrade`，进入 `pending_confirmation`；不是刷新页面就替换。
- 人工确认/人工调整的已有草稿保持人工结果；新规则可更新推荐说明，但不能清掉确认时间或覆盖已选类目。
- 数据已变且产生新冲突时，保留人工选择，同时展示新的冲突/资格告警；提交前统一校验，不能用“人工选过”跳过平台/尺码要求。

现 UI、预创建、新建、刷新、批量任务、历史回填都需消费同一决策，避免页面提示待确认但后台仍继续创建。
